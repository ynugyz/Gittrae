# 协作与提交规则

## 1. 先对齐，再开发

首轮任务仅阅读与核对。每个角色回复：我的职责、输入、输出、依赖、发现的问题、下一阶段交付物。不得把“创建交接包”当成开始应用开发的指令，也不反复询问已确认的T3、三数据域、150分钟、真实AI和保存恢复。

正式开发开始时，三名开发各自克隆本仓库到自己的电脑，使用相同基线commit。提交哈希以交接消息和 `git rev-parse HEAD` 为准；不把各电脑的绝对路径写入程序。

总控负责记录范围和接口决定；人员3把公共骨架、类型、样例和锁文件落入仓库。人员1/2可先按公共模拟样例实现自己的纯模块，最晚60分钟开始真实串联。

## 2. 分支与所有权

下列源代码目录是未来开发约定，当前没有实现。首轮不要创建这些目录或分支。

| 角色 | 分支 | 修改范围 |
|---|---|---|
| 总控 | docs/control（需要文档更新时） | handoff/decisions、接口状态索引与初始结构、任务与接口决定；不代写业务实现 |
| 人员1 | dev/data | src/data、数据适配相关测试；data/raw始终只读 |
| 人员2 | dev/analysis-ai | src/analysis、server、统计及模型接口相关测试 |
| 人员3 | dev/app | src/contracts、src/app、src/graph、src/storage、入口、依赖清单、锁文件、启动配置及集成测试 |
| 人员4 | audit/verification | acceptance/reports及独立核验材料；产品修复返回对应开发者 |

main由人员3统一集成。其他人提交模块分支，提供commit及核验结果；总控协调范围和顺序，人员4独立复验。无论谁合并，都不能覆盖或撤销其他人未确认的修改。

共享配置变更由人员3处理；人员2若模型代理需要新依赖，先给出要求，由人员3统一更新。所有模块引用src/contracts，不另建同名私有类型。

GitHub提交和合并只在正式开发获得明确启动后进行。新对话首轮不能自动向其他对话发送任务、创建PR或触发实现。需要跨对话调度时由总控在用户授权范围内协调，或通过仓库状态文档交接。

## 3. 交接格式

每次交接必须有：

1. 角色、分支、基线commit、当前commit。
2. 成果路径与调用方法（未实现时明确标记）。
3. 输入输出是否符合公共契约；任何变化及其批准记录。
4. 实际跑过的检查、输入、预期与结果，不用“应该正常”代替证据。
5. 遗留问题、影响、责任人、下一角色接手事项。

密钥不得写入代码、报告、截图或项目文件；API证据只记录时间、请求标识、模型、状态、分析编号和脱敏错误。

## 4. 角色4的独立性

审计从第一阶段准备口径和案例，最后30分钟集中验收。每个问题写复现步骤、期望、实际、影响、责任人和复验状态。审计人员不直接修改产品来让测试通过；开发者修复后提供新commit，审计基于该commit复验。

状态统一为 `not_started`、`in_progress`、`passed`、`failed`、`blocked`。交接包存在不等于应用passed；接口未实测不等于已连通。

## 5. 150分钟内的取舍

三类数据完整路径、正确统计、三图、真实AI、网络回源、保存恢复保持必做。停止增加图谱美化、跨域推理、开放问答和额外模型功能。出现阻塞时报告事实与影响，由总控安排原负责者处理，不能偷偷降低硬验收标准。

第20分钟查公共骨架与真实API；第60分钟开始集成；第90分钟查三类完整流程；第120分钟冻结功能；第150分钟按[总体验收标准](03_总体验收标准.md)交付。账号、额度和网络由队员准备，人员2验证，不能推迟到最终演示。

## 6. 每个接口的汇报入口与接手判断

固定入口为 [handoff/status/README.md](status/README.md)。按公共接口边界建立独立文件，另有一份公共契约状态；内部辅助函数不逐个建报告。索引只登记负责人、来源分支和依赖，不复制各文件的动态状态。

实现者维护接口文件中的实现、自测与未完成事项；下游维护接手及联调记录；人员4只在自己的审计报告中写独立复验结论，接口文件由负责人引用该报告。总控维护索引、依赖规则和裁决，不冒填他人的完成成绩。各角色可在原模块分支修改自己负责的接口状态文件；总控可初始化全部文件并记录经核对的仓库事实。

每份报告必须提供：接口ID、必要性、报告人/更新时间、契约版本及批准记录、来源分支、完整实现commit、成果路径、已完成与未完成、实际检查及证据、下游联调、独立审计、阻塞及责任人、候选下一步/前置条件/验收条件。报告commit使用文件历史取得，不在文件里伪造尚未产生的自身哈希。

状态仍只使用 not_started / in_progress / passed / failed / blocked，并说明针对哪个阶段、版本和数据。没看到远程成果写“未确认交付”；未做的检查写not_started；确有前置阻碍写blocked。开发者报告的passed须标明报告人和证据，不能改称总控或审计已复跑。修复或契约变更后，受影响的旧passed不能直接证明新commit；旧证据保留并标注需复验。

开始工作、准备接手和作阶段决策时，从GitHub读取相关负责分支的最新报告及其绑定commit；main上的同名文件可能滞后。若模块分支尚未包含本次规则，可只取本规则及该角色的状态文件，不合并无关产品改动。多分支状态有冲突时不按时间覆盖，先核对源commit和责任人；外部电脑未推送的工作不得被推断为没有开展。

下一步按四种目的判断：独立模块实现、模块自测、真实联调、最终签收。独立工作可在已确认契约和明确标记的MOCK输入下继续；真实联调须取得相容的上下游提交和真实数据；签收须有人员4在明确集成commit上的复验。一个接口未完成不自动阻止所有独立工作，也不能据此降低三域、真实AI和保存恢复的硬要求。

每次汇报的最后写清：该项是否必做；已经做到哪一步和证据；现在建议由谁做什么；缺什么时暂缓哪一步；完成后由谁按什么标准验收。状态记录和“可开始”判断本身不构成启动开发、付费调用或自动向其他对话发消息的授权。

在可交接提交/PR中附相关接口ID及状态文件；不要为每次微小修改另写重复周报。审计成果仍唯一保存在acceptance/reports，不复制313项参考检查为产品通过数。
